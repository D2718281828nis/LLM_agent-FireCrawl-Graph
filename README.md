# ИИ-ассистент для анализа клинических рекомендаций

Исследовательский проект демонстрирует, как LLM, реальные клинические рекомендации Минздрава России и граф знаний можно объединить для поддержки оператора телемедицины. Репозиторий содержит два Jupyter Notebook, описание научной новизны и таблицу сравнения агентов.

> **Важно:** проект является прототипом и не заменяет консультацию врача, диагностику или назначение лечения.

## Состав репозитория

| Файл | Назначение |
| --- | --- |
| `FireCrawl-CR-site-parsing.ipynb` | Собирает реестр клинических рекомендаций Минздрава (`clinical_recommendations_minzdrav.csv`) и извлекает через Firecrawl-агента текст алгоритма действий врача по выбранному ID; Mistral формирует проверяемое резюме. |
| `Telemed-conf-AI-assistant.ipynb` | Телемедицинский агент на базе Mistral и LangChain: ищет рекомендации в реестре из CSV (ground truth), при необходимости вызывает тот же Firecrawl-агент за реальным текстом, обходит игрушечный граф знаний и формирует подсказки оператору. |
| `clinical_recommendations_minzdrav.csv` | Реестр реальных клинических рекомендаций (ID, наименование, дата размещения, МКБ-10), результат работы `FireCrawl-CR-site-parsing.ipynb`. Служит ground truth для второго Notebook. |
| `clinical_recommendation_*_analysis.json` | Аудит извлечения по конкретному ID: сырой текст, полученный от Firecrawl-агента, и резюме Mistral — для сверки с официальным документом. |
| `doctor_algorithm_*.md` | Аудит распознавания «Приложения Б» по конкретному ID: схемы Mermaid с оценкой качества и предупреждениями (GitHub рисует их прямо в Markdown) — для сверки с оригиналом. |
| `agent_comparison.csv` / `.xlsx` | Результат сравнения ответов агента "с графом" и "без графа" на один и тот же кейс. |
| `scientific_novelty_graph_ai_agent.md` | Описание научной новизны графового подхода. |
| `.env.example` | Шаблон локальных секретов (копируется в `.env`, который не попадает в Git). |

## Как работает агент

Оба Notebook построены на одном и том же паттерне LangChain — **tool-calling агент** (`create_tool_calling_agent` + `AgentExecutor`), а не на жёстко закодированном сценарии. Это значит:

1. Модели (`ChatMistralAI`) даётся системный промпт с описанием доступных инструментов (`@tool`-функций) и задачи.
2. Агент получает запрос пользователя (жалобу пациента или, во втором Notebook, инструкцию извлечь текст рекомендации) и сам решает, какие инструменты и в каком порядке вызвать — это классический цикл **ReAct** (Reason → Act → Observe), который `AgentExecutor` крутит автоматически: вызывает выбранный инструмент, добавляет его результат в `agent_scratchpad`, снова спрашивает модель, что делать дальше, и так до тех пор, пока модель не решит, что данных достаточно для финального ответа.
3. Ни один инструмент не может «додумать» медицинский факт — каждый либо читает реальные данные (CSV-реестр, официальный документ через Firecrawl), либо детерминированно обрабатывает то, что вернул предыдущий инструмент. Роль LLM — планирование вызовов и связное изложение результата, а не источник фактов.

### Инструменты телемедицинского агента (`Telemed-conf-AI-assistant.ipynb`)

| Инструмент | Что делает |
| --- | --- |
| `search_clinical_guidelines_ru` | Ищет заболевание/МКБ-10 в `registry_df` — реестре из `clinical_recommendations_minzdrav.csv` (746 реальных записей, ground truth). Понимает несколько разговорных синонимов («гипертония» → «гипертенз» и т. п.) и возвращает до 5 совпадений с их ID. Дату размещения отдаёт в ISO-формате: в CSV она записана как M/D/YYYY, и «10/3/2024» модель на русском читала как 10 марта вместо 3 октября. |
| `fetch_clinical_recommendation_json` | По ID из предыдущего инструмента запускает **Firecrawl-агента** (тот же сценарий `extract_doctor_actions`, что и в `FireCrawl-CR-site-parsing.ipynb`) — он открывает официальный документ на `cr.minzdrav.gov.ru` и извлекает раздел «Приложение Б. Алгоритмы действий врача» (или разделы диагностики/лечения) в структурированный JSON, без пересказа. ID проверяется по реестру, произвольный URL сформировать нельзя. Результат кэшируется в рамках сессии — повторный запрос того же ID не бьёт в сеть заново. На практике «Приложение Б» почти всегда опубликовано картинкой, поэтому этот инструмент возвращает разделы диагностики и лечения, а само приложение даёт `get_doctor_algorithm_mermaid`. |
| `get_doctor_algorithm_mermaid` | По ID возвращает «Приложение Б. Алгоритмы действий врача»: проверяет, опубликовано ли оно текстом или изображениями, распознаёт блок-схемы vision-моделью Mistral и отдаёт каждую как граф Mermaid с оценкой качества `quality` (`ok` / `check` / `failed` / `not_flowchart`). Подробнее — в разделе «Алгоритм действий врача» ниже. |
| `query_clinical_knowledge_graph_ru` | Обходит `MEDICAL_KNOWLEDGE_GRAPH` — небольшой иллюстративный граф (утверждения/сущности/рекомендации и связи между ними) — и возвращает связанный подграф по проблеме пациента. Это самостоятельный учебный пример, не привязанный к реальному реестру. |
| `generate_operator_tips_from_graph` | Превращает JSON-результат предыдущего инструмента в конкретные подсказки оператору (например, предупреждает об опровергнутых утверждениях или напоминает уточнить сопутствующее заболевание). |
| `get_registry_overview` | Сводка по всему реестру: общее число КР, период размещения, доля пересмотренных и распределение всех КР по 22 классам МКБ-10. Используется агентом `ClinicalRegistryAnalystAgent` (Part III). |
| `get_clinical_guidelines_statistics` | Статистика по срезу реестра: число КР, доли и группировки по классам и рубрикам МКБ-10, году и месяцу размещения, номеру редакции, детям/взрослым с фильтрами по названию, коду МКБ-10 (`C34`, `C00-D48`, `II`; кириллица «С» тоже принимается), возрастной группе (`population`) и годам. Все числа, ранги и сравнения («самый крупный класс», «самая высокая доля пересмотренных») считаются детерминированно в pandas — LLM их только излагает. Используется агентом `ClinicalRegistryAnalystAgent` (Part III). |

Агент собирается в двух вариантах, чтобы наглядно показать пользу графа:

- **`TelemedicineAnalysisAgent`** ("с графом") — получает пять инструментов (поиск, Firecrawl, алгоритм действий врача и два графовых) и просят дать резюме, доказательную базу *и* подсказки оператору на основе графа.
- **`TelemedicineAnalysisAgentNoGraph`** ("без графа") — получает `search_clinical_guidelines_ru`, `fetch_clinical_recommendation_json` и `get_doctor_algorithm_mermaid`, то есть доказательную базу, но без интерпретации графом. Инструмент алгоритма есть у обоих вариантов, чтобы сравнение по-прежнему показывало вклад именно графа.

Оба варианта опираются на один и тот же реальный реестр и один и тот же Firecrawl-агент для текста рекомендации — разница именно в том, что даёт граф: интерпретацию фактов, опровержение мифов и структурированные подсказки, которых без графа нет. Ячейка `Part II - why graph?` запускает оба варианта на одном кейсе и сохраняет сравнение в `agent_comparison.csv`/`.xlsx`.

### Аналитический обзор реестра (`Part III - Registry analytics`)

Третий агент — **`ClinicalRegistryAnalystAgent`** — отвечает на аналитические вопросы о самом реестре: «сколько всего КР», «как они распределены по классам МКБ-10», «сколько КР по онкологии и какая доля из них пересмотрена», «сколько КР для детей и как они распределены по годам», «покажи алгоритм действий врача при мигрени». Он получает `get_registry_overview`, `get_clinical_guidelines_statistics`, `search_clinical_guidelines_ru` и `get_doctor_algorithm_mermaid` и при необходимости вызывает статистику несколько раз с разными фильтрами, чтобы сравнить срезы.

Модели бесплатного тарифа Mistral при проверке выдумывали числа и рейтинги («онкология — второй класс после травм» при том, что она первая). Поэтому ответ аналитика защищён не только промптом, но и кодом:

- **сравнения считает инструмент**, а не модель: у каждой группы есть `rank_by_count` и `rank_by_revised_share`, а готовые `leaders` и `highlights` («самая большая группа…», «самая высокая доля пересмотренных…», в том числе среди групп от 30 КР) модель только пересказывает;
- поле `scope` прямо говорит, относится ли таблица ко всему реестру или только к отфильтрованной выборке — раньше модель выдавала распределение внутри онкологии за распределение реестра;
- **автопроверка чисел**: после ответа код извлекает из него все числа и сверяет с данными, которые вернули инструменты. Если есть «чужие» числа, модель один раз переписывает ответ по исходным данным, а оставшиеся неподтверждённые числа явно помечаются предупреждением.

Перед агентом ячейка детерминированного обзора (без LLM) печатает ключевые цифры и строит два графика — КР по классам МКБ-10 и по году размещения. Раздел самостоятельный: достаточно выполнить ячейки импорта, инициализации и инструментов, Firecrawl не вызывается.

Особенности подсчёта:

- одна КР может относиться к нескольким классам МКБ-10 (например, «Трансплантация сердца» — T86.2 и Z94.1), поэтому сумма по классам больше числа КР;
- номер редакции берётся из суффикса ID (`762_2` — 2-я редакция);
- «дети/взрослые» определяются по названию КР (эвристика), у большинства КР возрастная группа в названии не указана.

### Алгоритм действий врача: «Приложение Б» → Mermaid (`Part IV`)

В выборке из 30 случайных КР «Приложение Б» было во всех 30: в 26 — только изображения блок-схем, в 4 — изображения и текст, текстовых — ни одного. Поэтому текстовое извлечение (Firecrawl) его не видит. `get_doctor_algorithm_mermaid` работает так:

1. Берёт документ из JSON API, которым пользуется сам сайт (`apicr.minzdrav.gov.ru`), — разделы приходят как HTML, изображения — base64-PNG. ID проверяется по реестру.
2. Определяет формат приложения: `image`, `text`, `mixed` или `missing`.
3. Каждое изображение распознаёт `ministral-14b-latest` в граф (блоки, стрелки, подписи «Да/Нет») по строгой pydantic-схеме; не-схемы (МРТ, рисунки) помечаются `not_flowchart`. Ответ модели с одной битой стрелкой не отбрасывается целиком — валидные блоки и стрелки сохраняются.
4. Mermaid строится из графа **кодом**, а не моделью — синтаксис всегда корректен, даже с кавычками, «<» и «>» в подписях.
5. Проверка: независимая расшифровка текста того же изображения (`mistral-ocr`, а на бесплатном тарифе, где у него лимит 0, — `ministral-8b-latest`) сверяется с подписями блоков. Так ловятся и выдуманные блоки, и **подмена слов** внутри блока; схема получает `quality=check` с перечнем неподтверждённых слов.
6. Агенты не переписывают Mermaid сами (при проверке модель ломала синтаксис): точные схемы прикладываются к ответу кодом в `result["doctor_algorithms"]`.

Проверка на 7 блок-схемах, размеченных вручную (5 — для настройки промпта, 2 — отложенные, размечены до просмотра ответов модели), по 2 прогона на финальном промпте:

| Что распознаётся | Точность / полнота |
| --- | --- |
| Блоки схемы | 0.99 / 0.96 |
| Текст блоков (сходство с оригиналом) | 0.98 |
| Подписи «Да/Нет» | 0.96 |
| Стрелки | 0.81 / 0.78 |
| Синтаксис Mermaid | 100% корректен |
| Не-схемы (МРТ, рисунки) распознаны как `not_flowchart` | 6 из 6 |

Проверка по расшифровке поймала все 3 замеченные подмены слов (например, «синдром старческой **астении**» → «…**артериальной гипертензии**») и дала одну ложную тревогу на 7 правильных схем. Ошибки стрелок (пропущенная или развёрнутая стрелка, слитые одинаковые блоки) автоматически не обнаруживаются — поэтому в демонстрации рядом со схемой всегда показывается оригинал, а ветвления нужно сверять с ним.

### Устойчивость к лимитам Mistral API

На бесплатном тарифе Mistral лимиты задаются **отдельно для каждой модели**: `mistral-small`, `mistral-medium`, `magistral-*` и `mistral-ocr` там недоступны (лимит 0 запросов в минуту), `mistral-large` закрыт тарифом, а `ministral-14b` даёт 30 запросов/мин, `ministral-8b` — 188, `ministral-3b` — 750. Поэтому:

- агенты работают на `ministral-14b-latest` (`MODEL_NAME` в ячейке инициализации) — самой сильной модели, доступной бесплатно;
- `mistral_rate_limiter(model)` создаёт **один общий** `InMemoryRateLimiter` на модель (с запасом 20% до лимита): агент и инструменты, работающие с одной моделью, делят её лимит, а не тратят его независимо;
- инструмент алгоритма повторяет вызов при `429` с паузой (`Retry-After` или 5, 10, 20, 40 с) — `max_retries` у `ChatMistralAI` повторяет только сетевые ошибки, а 429 без этой обёртки обрывает прогон. Если модель заблокирована тарифом (403 или лимит 0), повтора нет — сразу используется запасной путь.

### Как устроен `FireCrawl-CR-site-parsing.ipynb`

1. Реестр на `cr.minzdrav.gov.ru/clin-rec` не имеет постраничной навигации — только переключатель «Строк на странице» с опцией «Все». Notebook кликает по нему через Firecrawl, **сверяет счётчик «X из Y» на странице** и повторяет попытку с бэкоффом, если переключение не применилось — иначе можно молча получить только первые 5 записей.
2. Все строки разбираются локально через `pandas.read_html` (без LLM — быстрее и без риска, что модель «прочитает» таблицу неточно) и обрабатываются партиями с прогресс-баром, с проверкой количества ID на каждом шаге.
3. Для выбранного пользователем ID Firecrawl-агент (`extract_doctor_actions`) извлекает «Приложение Б» или ближайшие релевантные разделы прямо с официальной страницы, в структурированный JSON.
4. `ChatMistralAI` формирует резюме **только по извлечённому тексту** (без внешних знаний) с явными разделами: цель, действия врача, условия принятия решений, красные флаги, наблюдение, что проверить в оригинале.

Даты и содержание рекомендаций перед практическим применением необходимо сверять с официальным порталом Минздрава России: <https://cr.minzdrav.gov.ru>.

## Настройка секретов: Google Colab и локально/VS Code

Ключи в код и в Git **не вписываются**. Notebook сам определяет среду выполнения и берёт секрет из подходящего места:

```python
try:
    from google.colab import userdata
    IN_COLAB = True
except ImportError:
    IN_COLAB = False
    from dotenv import load_dotenv
    load_dotenv()
```

- **Google Colab** — секреты хранятся в Colab Secrets (значок ключа на левой панели) и подставляются через `google.colab.userdata` только во время выполнения сессии.
- **Локально / VS Code** — скопируйте `.env.example` в `.env` и впишите значения. `.env` заблокирован в `.gitignore` (`.env`, `.env.*`, кроме `.env.example`) и не может случайно попасть в коммит.

Нужны два секрета:

- `MISTRAL_API_KEY` — для `ChatMistralAI` в обоих Notebook;
- `FIRECRAWL_API_KEY` — для Firecrawl-клиента в обоих Notebook (сбор реестра, извлечение текста рекомендации).

Если секрет отсутствует, `require_secret(...)` останавливает выполнение понятной ошибкой с подсказкой, где его добавить — вместо того чтобы упасть глубже в стеке на первом сетевом вызове.

**Если ключ где-либо засветился** (чат, скриншот, публичный коммит) — считайте его скомпрометированным и немедленно отзовите/перевыпустите в кабинетах Mistral и Firecrawl. Удаление строки из репозитория не отменяет ключ и не убирает его из истории Git.

## Запуск

1. Сначала выполните `FireCrawl-CR-site-parsing.ipynb` сверху вниз — он создаст `clinical_recommendations_minzdrav.csv`, который служит ground truth для второго Notebook. Без этого файла `Telemed-conf-AI-assistant.ipynb` останавливается с понятной ошибкой при инициализации.
2. Настройте секреты — Colab Secrets (см. выше) или локальный `.env`.
3. Выполните `Telemed-conf-AI-assistant.ipynb` сверху вниз: он загрузит реестр, соберёт агентов и прогонит сравнение "с графом" / "без графа" на тестовом кейсе, сохранив результат в `agent_comparison.csv`/`.xlsx`, затем построит аналитический обзор реестра (Part III) и покажет распознанный алгоритм действий врача рядом с оригиналом (Part IV).
4. Сверяйте извлечённый текст и резюме с официальным документом по ссылке, которую печатает Notebook (`source_url`).

Зависимости устанавливаются в первых ячейках каждого Notebook.

## Ограничения

- Поиск в реестре основан на подстроковом сопоставлении и заранее заданных синонимах — может пропускать формулировки, которых нет в списке.
- Блок-схемы «Приложения Б» распознаются автоматически: текст блоков близок к дословному, но около 20% стрелок могут быть пропущены или направлены неверно — ветвления сверяйте с оригиналом.
- Модели бесплатного тарифа заметно слабее `mistral-small`: числа и сравнения в ответе аналитика защищены кодом, но формулировки и выводы агентов всё равно нужно проверять.
- `MEDICAL_KNOWLEDGE_GRAPH` — небольшой иллюстративный граф для демонстрации самой идеи, а не полная база медицинских знаний; он не привязан к реальному реестру.
- Извлечение текста рекомендации идёт через LLM-агента Firecrawl — это реальный сетевой запрос (секунды, иногда больше) и расход кредитов Firecrawl; результат зависит от структуры и доступности официального сайта.
- Ответ LLM в любом случае требует проверки медицинским специалистом и сверки с оригиналом документа.
- Перед обработкой реальных обращений необходимо обеспечить защиту персональных и медицинских данных.

## Рекомендации по безопасности

- не выводите ключи в ячейках, логах или сообщениях чата;
- не сохраняйте выполненный Notebook, если вывод содержит чувствительные данные;
- используйте отдельные ключи с минимальными правами для разработки;
- регулярно меняйте ключи и отзывайте их немедленно при малейшем подозрении на утечку;
- перед коммитом проверяйте изменения командой `git diff` и сканером секретов — особенно файлы, которые выглядят как данные (CSV, JSON), а не как код.
